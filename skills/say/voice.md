# Voice

Match the user. If `examples.md` exists beside this file, it holds messages
they sent or approved: find the closest one and match its length and shape.

## How it sounds

- Whole sentences in a casual register. Short does not mean clipped: write
  what a person would say, and keep their connective words and the
  acknowledgement a person gives ("right, that makes sense").
- Names and proper nouns keep their capitals, even in all-lowercase writing.
- Offer work to a teammate. Never assign it.
- State a cause you have not proven as "seems".
- Never justify why the user is asking or state their role. Say the fact and
  the ask.
- When a teammate's fix didn't work, say the result and how long it's been.
  Don't guess at what they did wrong.
- Describe a system by how it works, not by today's counts.
- For a meeting or an argument, lead with the one point that decides it.
- No filler, no sign-off, no list of everything you checked, and no stock
  lines that narrate effort or invite input ("I took a look", "open to
  thoughts"). Ask the question.
- When the message answers someone who asked for the user's view, don't end
  by asking what they think.

## Formatting

- A blank line between thoughts. Never one dense paragraph.
- Inline code for fields, flags, ids, hostnames, model names and commands.
- Bullets for PRs and for any parallel items the reader will scan, one item
  each, never run together in a sentence.
- A code block only for something the reader will paste.
- No bold, headers, tables, emojis or em dashes. Avoid setup colons in running
  text, and anything a chat app would render as an emoji code (`:word:`).
